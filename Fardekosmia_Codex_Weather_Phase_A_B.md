# Фардекосмия — ТЗ для Codex: биомы, World Data API и подготовка AtmosphericGrid

Версия: 1.0  
Дата: 2026-08-09

## 0. Цель задачи

Нужно развивать уже работающую погодную систему Фардекосмии **без переписывания существующего календаря, механики продвижения времени и истории WeatherState с нуля**.

Ближайшая работа делится на два этапа:

1. **Этап A — нормализовать биомы и единый доступ к глобальным картам мира.**
2. **Этап B — построить фундамент глобальной атмосферной сетки AtmosphericGrid**, на которой позже будут работать давление, ветер, перенос тепла/влаги, облачность и осадки.

Этап A должен быть реализован первым и полностью покрыт тестами. Этап B можно начинать сразу после того, как Этап A стабильно проходит тесты.

---

# 1. Важное: что уже работает и что нельзя ломать

Существующая система уже имеет:

- `Campaign.world_minutes` как единое игровое время;
- календарь с Витками, сезонами, Кругом Лика и фазами;
- `RegionalSky`;
- локальное время по долготе;
- видимость Ympha;
- Светлые / Тёмные / Смешанные сезоны;
- `Region` с климатическими параметрами и координатами;
- `WeatherState` с историей погоды;
- детерминированный weather seed;
- `weather_update_interval_minutes` (по умолчанию 360 минут);
- создание всех промежуточных погодных снимков при большом продвижении времени;
- `select_for_update()` и транзакционное продвижение времени;
- откат всей операции при ошибке;
- запрет создания погоды GET-запросами;
- уникальный погодный снимок региона на конкретную игровую минуту.

**Не удалять и не переписывать этот фундамент без необходимости.**

Новая система должна постепенно заменить только упрощённую физику погоды, сохранив совместимость с текущим UI и существующими кампаниями.

# 5. Этап A — единый World Data API

Сейчас `base_temperature`, `elevation` и `biome` предлагаются региону при создании, после чего становятся отдельными сохранёнными значениями. Это нужно сохранить для обратной совместимости, но добавить единый слой чтения глобальных карт.

Нужен сервис уровня:

```python
world/services/world_data.py
```

или эквивалент согласно архитектуре проекта.

Минимальный API:

```python
surface_at(latitude, longitude)
elevation_at(latitude, longitude)
mean_temperature_at(latitude, longitude)
biome_at(latitude, longitude)
```

Также подготовить API, чтобы позже без ломки добавить:

```python
distance_to_ocean(latitude, longitude)
ocean_temperature_at(latitude, longitude, world_minutes=None)
albedo_at(latitude, longitude)
```

## 5.1. Требования к координатам

- долгота должна корректно wrap-around на границе карты;
- широта должна быть clamp/validated в допустимом диапазоне;
- преобразование координат в пиксель карты должно быть единообразным для всех слоёв;
- не дублировать формулу преобразования `lat/lon -> pixel` в нескольких сервисах;
- предусмотреть карту equirectangular, если именно так устроены текущие слои;
- если существующая карта использует другую проекцию, использовать реальную текущую реализацию, а не подменять её предположением.

## 5.2. Источник истины

Статические мировые карты должны стать каноническим источником пространственных данных:

- поверхность;
- высота;
- средняя температура;
- биом.

Но `Region` пока **не лишать** старых полей.

Нужен режим совместимости:

```text
World layer = spatial truth
Region fields = snapshot/override/legacy compatibility
```

Конкретную политику override оформить явно в коде и документации.

Рекомендуемый первый вариант:

1. `world_data` возвращает карту;
2. старые поля Region продолжают работать для существующего weather-v2;
3. новый AtmosphericGrid читает непосредственно World Data API;
4. позже можно отдельно решить, какие поля Region становятся override.

# 6. Биом НЕ должен жёстко генерировать климат

На этом этапе **не добавлять большой набор правил вида**:

```python
if biome == RED_PLATEAUS:
    humidity -= 30
    precipitation -= 0.5
```

Биом — вторичный фактор поверхности.

Принцип новой системы:

```text
география + освещение + океан + рельеф + атмосфера
                    ↓
                 климат
                    ↓
                  биом
                    ↓
        вторичная обратная связь
```

Пример: Красные Плато канонически сухие главным образом из-за дождевой тени за горами. AtmosphericGrid позже должен уметь получить эту сухость через перенос влаги и орографические осадки, а не потому что слово `RED_PLATEAUS` насильно отключает дождь.

Допустимы только мягкие surface modifiers, которые не являются главным климатообразующим механизмом, например:

- испарение/эвапотранспирация растительности;
- roughness поверхности;
- теплоёмкость поверхности;
- альбедо;
- доступность поверхностной воды;

Но их реализацию можно отложить на следующий этап.

# 7. Этап B — AtmosphericGrid: архитектурный фундамент

После завершения Этапа A создать глобальную расчётную атмосферную сетку.

На первом этапе сетка не должна быть полноценной CFD/метеомоделью. Нужна упрощённая, стабильная и детерминированная система, достаточная для RPG/GM мира.

## 7.1. Начальное разрешение

Предпочтительно начать с:

```text
180 x 90 = 16 200 атмосферных ячеек
```

Сделать разрешение конфигурируемым.

Не хранить каждую ячейку каждого 360-минутного шага как отдельную Django row, если это создаёт десятки тысяч записей на шаг.

Нужен компактный формат состояния: массивы / blob / сериализованная матрица / специализированная модель snapshot, исходя из текущего стека проекта.

Перед выбором формата оценить объём данных и стоимость сериализации.

## 7.2. Минимальные динамические поля ячейки

```python
temperature_c
relative_humidity
pressure_hpa
wind_u
wind_v
cloud_cover
```

Можно дополнительно заложить, но не обязательно сразу включать в расчёт:

```python
precipitable_water
precipitation_rate
surface_temperature
```

## 7.3. Статические поля ячейки

Получать через World Data API:

```python
surface_type
terrain_elevation_m
mean_temperature_c
biome
latitude
longitude
```

Позже:

```python
ocean_fraction
surface_albedo
distance_to_ocean
```

# 8. Ветер

Текущий `wind_speed = random.gauss(...)` считать временным legacy-механизмом.

Новая модель должна хранить двумерный вектор:

```python
wind_u  # запад-восток
wind_v  # юг-север
```

Из него вычислять для UI:

```python
wind_speed
wind_direction_deg
```

Постепенно ветер должен зависеть от:

1. градиента давления;
2. широты;
3. вращения/эффекта Кориолиса в упрощённой форме;
4. трения о поверхность;
5. рельефа;
6. температурных контрастов суша/океан;
7. предыдущего атмосферного состояния.

Не делать направление полностью случайным на каждом шаге.

---

# 9. Давление

Добавить `pressure_hpa` как физический драйвер ветра.

На первом прототипе давление может быть упрощённым полем, связанным с:

- температурной аномалией;
- высотой;
- предыдущим давлением;
- соседними ячейками;
- мягким детерминированным возмущением.

Главное требование: соседние различия давления должны создавать связный ветер, а не независимый random для каждой ячейки.

---

# 10. Перенос между ячейками

AtmosphericGrid должен поддержать перенос:

- тепла;
- водяного пара / влажности;

по полю ветра.

Можно использовать упрощённую semi-Lagrangian advection или другую устойчивую схему, если она достаточно проста и тестируема.

Главное функциональное поведение:

```text
горячий океан -> воздух получает тепло и влагу
ветер -> переносит их на сушу
горы -> меняют воздушный поток и вызывают подъём
наветренная сторона -> больше осадков
подветренная сторона -> суше
```

---

# 11. Горячий океан Фардекосмии

Это канонически важный фактор мира.

Не считать океан обычным земным холодным резервуаром.

Архитектура должна позволять отдельное поле/функцию:

```python
ocean_temperature_at(latitude, longitude, world_minutes)
```

Даже если точная температура океана пока не закреплена, нельзя хардкодить земное значение.

На этапе первого AtmosphericGrid допустим параметр кампании / world config:

```python
mean_ocean_temperature_c
```

или климатическая океаническая карта.

Океан должен в будущем влиять на:

- испарение;
- абсолютное содержание влаги;
- ночное/долговременное удержание тепла;
- прибрежный климат;
- образование мощных штормов.

Не подменять это простым `coast humidity + 10`.

---

# 12. Высоты и полярные льды

Высотная карта должна использоваться напрямую AtmosphericGrid.

Учитывать:

- снижение температуры с высотой;
- влияние высоты на давление;
- препятствие потоку воздуха;
- орографический подъём;
- дождевую тень.

Полярные зоны Фардекосмии включают мощные ледовые щиты и высокие плато. В будущем понадобится `albedo/ice_fraction`.

Пока не смешивать физическую высоту рельефа и будущий surface-albedo в одно поле.

---

# 13. Астрономия и сезонность — пока интерфейс, не финальная физика

Не удалять существующие:

- `CalendarMoment`;
- `RegionalSky`;
- Витки;
- сезоны;
- видимость Ympha;
- Рассветание / Угасание.

Но не смешивать два разных эффекта:

1. локальный ночной вклад видимой Ympha;
2. изменение общего потока центральной звезды из-за орбиты всей системы Ympha вокруг звезды.

Для будущей модели подготовить интерфейсы:

```python
stellar_distance_au(world_minutes)
stellar_flux_factor(world_minutes)
ympha_local_exposure(latitude, longitude, world_minutes)
```

Точные абсолютные орбитальные параметры сейчас не придумывать как канон.

Известное требование мира: орбита Ympha вокруг центральной звезды сильно вытянута, и в тёплой части года система примерно на 5 AU ближе к звезде, чем в холодной. Абсолютные periapsis/apoapsis пока должны быть конфигурируемыми.

# 14. Как Region должен получать погоду в будущем

Целевая архитектура:

```text
World Data Maps
      ↓
AtmosphericGrid(t)
      ↓
interpolate/sample at Region coordinates/polygon
      ↓
WeatherState
      ↓
existing Region UI
```

То есть `WeatherState` не нужно выбрасывать.

Он должен стать RPG-friendly snapshot, полученным из глобальной атмосферы.

Для региона выводить как минимум:

- temperature;
- humidity;
- wind_speed;
- wind_direction;
- pressure;
- precipitation;
- condition;
- позже cloud_cover / visibility / gusts.

Существующий UI можно мигрировать постепенно.

# 15. Детерминизм

Текущая система воспроизводима по seed.

Это свойство сохранить.

AtmosphericGrid при одинаковых:

- campaign initial state;
- world config;
- world_minutes;
- статических картах;

должен приводить к одному и тому же состоянию.

Нельзя использовать глобальный непредсказуемый random без seed.

При необходимости генерация шумов должна быть привязана к:

```text
campaign/world seed + atmospheric step + cell coordinates
```

# 16. Временные шаги

Сохранить существующую идею weather boundary.

По умолчанию:

```text
360 минут
```

Если пользователь продвигает время через несколько границ, AtmosphericGrid должен пройти **каждый промежуточный шаг последовательно**, а не прыгнуть сразу в конечную точку.

Это необходимо для переноса воздушных масс и устойчивости симуляции.

Существующий лимит переходов и транзакционность учитывать.

Если глобальная сетка делает старый лимит слишком дорогим, сначала измерить производительность и предложить безопасную оптимизацию, а не молча менять семантику времени.

# 17. Тесты Этапа A

Минимум покрыть:

### Biome enum
- все 16 биомов существуют;
- русские display labels корректны;
- старые сохранённые значения мигрируются без потери данных;
- `Побережье` не теряется молча.

### World coordinates
- `(lat, lon)` правильно превращаются в координату карты;
- долгота wrap-around работает;
- северный и южный края не инвертированы;
- центр карты читается одинаково всеми слоями.

### World Data API
- `elevation_at()` возвращает значение из высотной карты;
- `mean_temperature_at()` — из температурной;
- `biome_at()` — из слоя биомов;
- `surface_at()` различает сушу/океан;
- результат не зависит от того, существует ли Region в этой точке.

### Compatibility
- существующая страница региона открывается;
- старый WeatherState читается;
- продвижение времени всё ещё работает;
- GET не создаёт новые WeatherState.

# 18. Тесты первого AtmosphericGrid

После появления Этапа B проверить не только значения, но и качественное поведение.

### 18.1. Persistence
Одно и то же начальное состояние не должно превращаться в хаотически несвязанные карты через один шаг.

### 18.2. Pressure -> wind
Искусственно созданный градиент давления должен давать поток в ожидаемую сторону до поправок на вращение/трение.

### 18.3. Advection
Область повышенной влажности должна перемещаться по направлению заданного ветра.

### 18.4. Ocean moisture
При прочих равных воздух, проходящий над горячим океаном, должен получать больше влаги, чем воздух над сухой сушей.

### 18.5. Mountains
При потоке влажного воздуха через высокий хребет наветренная сторона должна становиться влажнее/осадочнее, а подветренная — суше.

### 18.6. Determinism
Повторный расчёт из одинакового snapshot и seed даёт идентичный результат.

### 18.7. Time stepping
Шаг `+24 часа` через четыре 6-часовые границы должен давать тот же результат, что четыре последовательных продвижения `+6 часов`, если между ними не менялись внешние данные.

# 19. Нефункциональные требования

- Не делать N+1 запросы на каждую атмосферную ячейку.
- Глобальные карты загружать/кэшировать разумно.
- Не декодировать один и тот же PNG десятки тысяч раз за шаг.
- Чётко отделить static world layers от dynamic atmospheric state.
- Новую физику размещать в services, а не во views/templates.
- Все коэффициенты прототипа помечать как настройки, а не канон мира.
- Не хардкодить неизвестные параметры атмосферы, океана или орбиты как «реальные значения Фардекосмии».
- Добавить документацию о единицах измерения.

# 21. Что НЕ делать в этой задаче

Пока не требуется:

- полноценная Navier–Stokes CFD;
- прогноз на недели вперёд;
- визуализация красивых animated wind particles;
- накопление снега/луж/паводков;
- финальная модель приливов;
- финальная модель Жарной Порчи;
- финальная модель Ноктиса/Люмена;
- ручные подробные погодные коэффициенты для всех 16 биомов;
- окончательная калибровка атмосферы Земли;
- окончательные значения орбиты Ympha.

Но архитектура не должна блокировать эти функции позже.

# 23. Главный критерий готовности

Этап A считается готовым, когда любой код проекта может спросить:

```python
world_data.biome_at(lat, lon)
world_data.elevation_at(lat, lon)
world_data.mean_temperature_at(lat, lon)
world_data.surface_at(lat, lon)
```

и получить согласованный ответ из глобальных слоёв мира без необходимости существования Region.

Первый AtmosphericGrid считается успешным, когда погода начинает быть **пространственно связанной**: воздух переносит тепло и влагу между соседними областями, ветер имеет направление, давление влияет на поток, горячий океан является источником влаги/тепла, а горы способны создавать наветренную влажную и подветренную сухую зоны.
